# AUTOSAR Agentic Workflow with LangGraph — Design

**Author:** Chandmare, Kunal  
**Model:** Grok  
**Created:** 2026-10-21  
**Updated:** 2026-10-21  
**Purpose:** LangGraph-based multi-agent design for translating natural-language requests into AUTOSAR concepts.  
**First milestone:** Validate that the AUTOSAR Translator reliably produces a structured State usable by downstream Specs agents that are version-aware (e.g. AUTOSAR 20-11, R22-11, etc.).

## Goal (Phase 1)

Prove that an **AUTOSAR Translator** node (powered by an LLM available in the same runtime/framework) can:

1. Accept a user request (or a lightly structured intent).
2. Produce a **version-aware, structured State** that accurately captures AUTOSAR elements.
3. Make that State immediately useful for a **Specs Agent** that knows the exact AUTOSAR release (e.g. “Signals for 20-11”) and can later scan requirements, look up meta-model rules, or retrieve specification excerpts.

Everything else (full generation, ARXML emission, multi-step planning) is deferred until the Translator → structured State path is solid.

## LangGraph Architecture

Use a **LangGraph `StateGraph`** with a single shared typed State.  
LLM calls are made through the framework’s available model interface (same process / same credentials / same endpoint used by other agents in the system).

### Core State Schema (optimized for Spec Agent)

The State is designed so the Spec Agent can directly consume it and collect the relevant specification items without re-parsing the original user request.

```python
from typing import TypedDict, Optional, List, Dict, Any, Literal
from pydantic import BaseModel, Field

class SpecTarget(BaseModel):
    """Explicit target that tells the Spec Agent exactly what to retrieve from the standard."""
    autosar_release: str                       # e.g. "20-11"
    document: str                              # e.g. "AUTOSAR_TPS_SystemTemplate", "AUTOSAR_SWS_COM", "AUTOSAR_EXP_AISpecification"
    chapter_or_section: Optional[str] = None   # e.g. "7.2 SystemSignal", "Communication Management"
    meta_model_element: str                    # e.g. "SystemSignal", "ISignal", "SenderReceiverInterface"
    required_items: List[str] = Field(default_factory=list)  # ["mandatory attributes", "constraints", "examples", "related requirements"]
    keywords: List[str] = Field(default_factory=list)        # for search/RAG

class AutosarElement(BaseModel):
    """Version-aware AUTOSAR element produced by Translator."""
    name: str
    kind: Literal[
        "SoftwareComponent", "Port", "Interface", "DataElement",
        "Signal", "SystemSignal", "ISignal", "Pdu", "Runnable", "DataType",
        "System", "ECU", "CommunicationCluster", "Other"
    ]
    autosar_release: str
    attributes: Dict[str, Any] = Field(default_factory=dict)
    references: List[str] = Field(default_factory=list)
    confidence: float = 1.0
    notes: Optional[str] = None
    # Direct link to what the Spec Agent should collect
    spec_targets: List[SpecTarget] = Field(default_factory=list)

class CollectedSpecItem(BaseModel):
    """What the Spec Agent returns after scanning the standard."""
    source_document: str
    release: str
    section: Optional[str] = None
    content_summary: str
    raw_excerpt: Optional[str] = None
    constraints: List[str] = Field(default_factory=list)
    mandatory_attributes: List[str] = Field(default_factory=list)
    related_requirements: List[str] = Field(default_factory=list)

class AutosarState(TypedDict):
    # Input
    user_request: str
    requested_autosar_release: Optional[str]

    # Intermediate
    intent: Optional[Dict[str, Any]]

    # Translator output
    elements: List[AutosarElement]
    translation_summary: str
    ambiguities: List[str]
    missing_information: List[str]

    # Spec Agent contract — primary interface
    spec_targets: List[SpecTarget]          # aggregated from all elements (or generated by Translator)
    collected_spec_items: Optional[List[CollectedSpecItem]]

    # Control / metadata
    current_node: str
    errors: List[str]
    messages: List[Dict[str, str]]
```

**How this helps the Spec Agent**

- `spec_targets` (and `elements[].spec_targets`) give precise document + section + meta-model element + list of items to collect.
- No need for the Spec Agent to guess which AUTOSAR PDF/chapter to open.
- `CollectedSpecItem` is the structured result the Spec Agent writes back, so later nodes receive clean, version-specific specification content.
- Translator is responsible for emitting good `spec_targets`; Spec Agent only has to execute the retrieval and fill `collected_spec_items`.

### 3. Specs Agent Node

**Responsibility:**  
Given the structured `spec_targets` (and `elements`), collect the relevant specification items from the correct AUTOSAR release.

**Input it relies on:**
- `requested_autosar_release`
- `spec_targets` / `elements[].spec_targets`

**Output it writes:**
- `collected_spec_items`

### Making / Training the Spec Agent to Understand Only AUTOSAR

The Spec Agent must stay strictly inside the AUTOSAR domain and be release-aware. Recommended approach (in order of practicality):

1. **System prompt + role constraint (immediate)**
   - Strong system prompt: “You are an AUTOSAR specification retrieval specialist. You only answer using official AUTOSAR documents for the exact release requested. Never invent requirements. If the information is not in the provided context, say so.”
   - Explicitly forbid general automotive knowledge that is not from AUTOSAR.

2. **Versioned Retrieval-Augmented Generation (primary method)**
   - Index the official AUTOSAR specifications (TPS, SWS, EXP, RS, etc.) per release (20-11, R22-11, 4.4.0, …).
   - Store metadata: release, document ID, chapter, section, meta-model element.
   - Spec Agent’s tools only search this index; no open-web or general LLM knowledge for factual AUTOSAR content.
   - Chunk by section or by meta-model class so retrieval is precise.

3. **Structured output + tool calling**
   - Force the Spec Agent to return only `CollectedSpecItem` objects.
   - Provide tools such as `search_autosar_spec(release, document, query)` and `get_section(release, document, section)`.

4. **Fine-tuning / continued pre-training (optional, later)**
   - If you have licensed AUTOSAR document text, fine-tune a smaller model on:
     - Question → relevant section + constraints
     - Meta-model element → mandatory attributes + related requirements
   - Keep a held-out set of release-specific questions for evaluation.
   - Prefer RAG first; fine-tuning is useful mainly for style and ranking.

5. **Evaluation & guardrails**
   - Test suite of known AUTOSAR requirements per release (e.g. “What are the mandatory attributes of SystemSignal in 20-11?”).
   - Reject or flag answers that cite the wrong release or invent attributes.
   - Optional human review loop for high-impact elements.

6. **Knowledge isolation**
   - Run the Spec Agent with a dedicated context window / separate LangGraph node that does not see general chat history.
   - Pass only the `spec_targets` and the retrieved chunks.

With the revised State, the Translator already prepares the exact targets; the Spec Agent’s job reduces to reliable, release-correct retrieval and structuring of the specification items.

### 1. Intent Node (lightweight, optional for first tests)

- Input: `user_request`
- Output: fills `intent` with request_type, entities, explicit version hints.
- Can be skipped initially; Translator can work directly from `user_request` + `requested_autosar_release`.

### 2. AUTOSAR Translator Node (primary milestone)

**Responsibility:**  
Turn the request into a list of version-aware `AutosarElement` objects, each carrying precise `spec_targets` that the Spec Agent can execute directly.

**LLM prompt guidelines (to be refined):**

- You are an AUTOSAR domain expert.
- The target release is given (default to the value in state, e.g. `20-11`).
- Map every concept the user mentions to the correct meta-model element for that release.
- For every element, emit one or more `spec_targets` that name the exact document, section (if known), meta-model element, and the list of items the Spec Agent should collect (mandatory attributes, constraints, related requirements, examples, …).
- Always emit the structured fields: elements, translation_summary, ambiguities, missing_information.
- Never invent elements that are not supported or named differently in the requested release.

**Expected structured output (forced via tool / structured output / JSON mode):**

```json
{
  "elements": [
    {
      "name": "VehicleSpeed",
      "kind": "SystemSignal",
      "autosar_release": "20-11",
      "attributes": {"length": 16},
      "spec_targets": [
        {
          "autosar_release": "20-11",
          "document": "AUTOSAR_TPS_SystemTemplate",
          "chapter_or_section": "SystemSignal",
          "meta_model_element": "SystemSignal",
          "required_items": ["mandatory attributes", "constraints", "related ISignal mapping rules"],
          "keywords": ["SystemSignal", "length", "SystemSignalGroup"]
        }
      ]
    }
  ],
  "translation_summary": "...",
  "ambiguities": [],
  "missing_information": ["exact bit length confirmation"]
}
```

### 3. Specs Agent Node

**Responsibility:**  
Consume the Translator’s `spec_targets` and collect the relevant specification items from the exact AUTOSAR release.

**Key behaviors:**

- Reads `requested_autosar_release` and every `spec_targets` entry.
- Uses the document / section / meta-model element / keywords to retrieve the correct parts of the standard.
- Example: if the user asked for Signals and the release is `20-11`, the Spec Agent opens the 20-11 System Template (or Communication specification) and extracts mandatory attributes, constraints, and related requirements for SystemSignal / ISignal.
- Writes the results into `collected_spec_items`.
- Can be backed by versioned RAG, a curated knowledge base, or tools that only expose AUTOSAR documents.

#### Spec Agent System Prompt

Use the following system prompt (or a close variant) for the Spec Agent node. It forces the agent to search only AUTOSAR specifications of the requested release and to return structured `CollectedSpecItem` results.

```text
You are an AUTOSAR Specification Retrieval Specialist.

Your only job is to search and extract information from official AUTOSAR specification documents for the exact release given in the request.

Rules you must follow:
1. Use only the AUTOSAR release specified in the SpecTarget (or the requested_autosar_release). Never mix releases.
2. Search only official AUTOSAR documents (TPS, SWS, EXP, RS, MOD, etc.). Do not use general knowledge, web results, or non-AUTOSAR sources.
3. For every SpecTarget you receive, retrieve the relevant sections and extract exactly the items listed in required_items (mandatory attributes, constraints, related requirements, examples, etc.).
4. Always cite the source document, release, and section (when available).
5. If the information is not present in the retrieved AUTOSAR content, explicitly state that it was not found. Do not invent attributes, constraints, or requirements.
6. Return results strictly as a list of CollectedSpecItem objects with the fields:
   - source_document
   - release
   - section
   - content_summary
   - raw_excerpt (short, relevant quote if available)
   - constraints
   - mandatory_attributes
   - related_requirements

Input you will receive:
- One or more SpecTarget objects (document, chapter_or_section, meta_model_element, required_items, keywords, autosar_release)
- Optional retrieved document chunks from the AUTOSAR knowledge base

Process:
- For each SpecTarget, formulate precise searches using the keywords, meta_model_element, and document name.
- Prefer the exact chapter/section when provided.
- Extract only what the standard states for that release.
- Aggregate the findings into CollectedSpecItem entries.

You must not:
- Answer general automotive or software questions outside AUTOSAR.
- Guess or complete missing information from other releases or from training data.
- Produce ARXML, code, or design recommendations — only specification content.
```

This prompt can be combined with tool-calling (e.g. `search_autosar_spec(release, document, query)`) so the agent actually retrieves chunks before answering.

## How the Revised State Helps the Spec Agent

| Translator produces | Spec Agent uses it for |
|---------------------|-------------------------|
| `elements[].spec_targets` | Exact document + section + meta-model element + list of items to collect |
| `spec_targets` (aggregated) | Batch retrieval without re-interpreting the user request |
| `autosar_release` on every target | Guarantees the correct release is opened (20-11 vs R22-11 vs 4.4.0) |
| `required_items` | Tells the agent whether to extract attributes, constraints, examples, or requirements |
| `ambiguities` / `missing_information` | Focuses retrieval on uncertain areas |

## First Goal — Success Criteria for the Translator

The Translator is considered “working” when, for a set of representative requests:

1. The structured State is always valid (schema-compliant).
2. Element kinds and names are correct for the requested release.
3. Every relevant element carries accurate `spec_targets` (correct document, release, and meta-model element).
4. `spec_targets` are specific enough that a Spec Agent can collect the required specification items without re-interpreting the original user text.
5. Ambiguities and missing information are explicitly listed instead of being silently guessed.

Example test requests to start with:

- “Create a Signal for vehicle speed, 16-bit, in AUTOSAR 20-11.”
- “I need a Software Component with a required port that receives an ISignal of type VehicleSpeed according to R22-11.”
- “Map a CAN signal to an Application Data Type for release 4.4.0.”
